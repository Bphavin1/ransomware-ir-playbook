Phase 1 Preparation NIST SP 800-61 § 3.1

Preparation is the most critical phase. An organization that cannot contain ransomware in the first 30 minutes will likely face full-environment encryption. This phase must be completed before an incident occurs.

Roles and Responsibilities

Incident Response Team

  • IR Lead — declares incidents, owns the response timeline
  • SOC Analyst — triage and initial investigation
  • Network Engineer — firewall changes, VLAN isolation
  • Endpoint Engineer — host isolation and forensics
  • Threat Intelligence Analyst — IOC enrichment

Executive and Legal

  • CISO — escalation authority and ransom decisions
  • Legal Counsel — regulatory notification obligations
  • Communications — internal and external messaging
  • Executive Sponsor — business continuity decisions
  • HR — if insider threat is suspected
Pre-Incident Requirements
  • Wazuh SIEM deployed with File Integrity Monitoring (FIM) enabled on all endpoints
  • Offline, immutable backups tested within the last 30 days (3-2-1 backup rule enforced)
  • Endpoint Detection and Response (EDR) agent deployed org-wide
  • Network segmentation documented — VLAN map current and accurate
  • Emergency contact list printed and stored offline (phone tree for no-email scenarios)
  • Out-of-band communication channel established (Signal group, secondary email domain)
  • Tabletop exercise completed in last 12 months
  • IR retainer active with a third-party forensics firm
  • Cyber insurance policy reviewed — ransomware coverage confirmed
  • AD tiering model in place — privileged accounts separated from standard users
  • Privileged Access Workstations (PAWs) deployed for admin tasks
  • MFA enforced on VPN, email, and all remote access
Key Assets and Dependencies

Document Before an Incident

  • Crown jewel asset list — systems that, if encrypted, trigger a P1 declaration
  • Domain controller hostnames and IP addresses
  • Backup infrastructure IPs — ensure they are on an isolated VLAN
  • EDR console URL and break-glass credentials (stored in offline vault)
  • Wazuh dashboard URL — 10.0.0.130:443 (or current IP)
  • Firewall management console — emergency block procedures
! If backups are connected to the production network, ransomware will encrypt them. Verify backup isolation before an incident occurs — not during one.
Phase 2 Detection and Analysis NIST SP 800-61 § 3.2

Ransomware rarely detonates immediately after initial access. Attackers typically spend 1 to 14 days in the environment performing reconnaissance and credential harvesting before executing the payload. Early detection during the pre-encryption phase is the highest-value opportunity to prevent catastrophic impact.

Wazuh SIEM — Primary Detection Rules
i Monitor these rules in Wazuh at 10.0.0.130. Navigate to Security Events and filter by Rule ID or Group to focus on ransomware-related activity.
Rule ID Group / Module Alert Description Severity Ransomware Relevance
550 syscheck / FIM Integrity checksum changed on monitored file High (7) Mass checksum changes signal active encryption
553 syscheck / FIM File added to monitored directory Medium (5) Ransom note files dropped (README.txt, DECRYPT.html)
554 syscheck / FIM File deleted from monitored directory Medium (5) Original files deleted after encryption (double-extension pattern)
87103 syscheck / FIM Possible ransomware — mass file modification detected Critical (12) Composite rule: high-volume FIM events in short window
87105 syscheck / FIM Suspicious file extension change detected (.locked, .enc, .crypt) Critical (12) Direct indicator of encryption in progress
5402 ossec / sudo Successful sudo to root High (8) Privilege escalation stage prior to encryption
60112 ossec / auditd Multiple file permission changes in short period High (8) Ransomware modifying ACLs before encrypting files
61603 windows / defender Windows Defender malware detection event Critical (12) AV detection of ransomware payload or dropper
61604 windows / defender Windows Defender real-time protection disabled Critical (12) T1562 — Impair Defenses, common pre-encryption step
92200 sysmon Suspicious process creation — LOLBin or encoded payload High (9) PowerShell, wscript, certutil used to execute payloads
92656 windows / eventlog Windows Security event log cleared Critical (12) T1070.001 — log clearing before encryption detonation
40111 ossec / ids Multiple authentication failures followed by success High (10) Brute force / credential spray leading to initial access
31168 windows / eventlog VSS shadow copy deleted (vssadmin delete shadows) Critical (15) T1490 — Inhibit System Recovery, nearly always ransomware
100200 custom / local_rules Outbound connection to known ransomware C2 IP Critical (13) C2 beacon detected — attacker has active foothold
Detection Checklist
  • Identify the first alert timestamp — establish Patient Zero and initial compromise window
  • Determine scope: how many hosts show FIM rule 550/553/554 activity?
  • Check for VSS deletion (Rule 31168) — if present, assume no Windows Shadow Copy recovery
  • Identify the encryption file extension (.locked, .enc, .crypt, .ryk, .conti, etc.)
  • Search for ransom note filenames across file shares
  • Check for outbound connections to unknown IPs from affected hosts
  • Determine if Domain Controllers are affected — if yes, escalate to P1 immediately
  • Identify the likely initial access vector: phishing email, exposed RDP, vulnerable VPN
  • Assign a severity rating (P1 Critical / P2 High / P3 Medium) and document
  • Notify CISO and legal within SLA (default: P1 = 15 minutes)
Wazuh Query Commands
Search FIM events on Wazuh Manager
# SSH into Wazuh Manager
ssh wazuh-user@10.0.0.130

# Search recent FIM alerts (rule 550, 553, 554)
grep -E "Rule: (550|553|554|87103|87105|31168)" /var/ossec/logs/alerts/alerts.log | tail -100

# Search for ransomware-related file extensions in FIM events
grep -i "\.(locked|enc|crypt|ryk|conti|hive|pay2key)" /var/ossec/logs/alerts/alerts.log

# Count FIM events per agent in last hour (mass encryption indicator)
grep "syscheck" /var/ossec/logs/alerts/alerts.log | awk '{print $8}' | sort | uniq -c | sort -rn | head -20

# Check for VSS deletion events (T1490)
grep "vssadmin\|wmic.*shadowcopy" /var/ossec/logs/alerts/alerts.log -i
! Do not reboot affected systems during detection. Memory forensics may capture encryption keys, running processes, and attacker tooling. Capture volatile data first.
Phase 3 Containment NIST SP 800-61 § 3.3

Speed is critical. Every minute of dwell time allows ransomware to encrypt additional hosts and spread laterally. Containment must balance the need for speed against the risk of tipping off the attacker and causing them to accelerate or destroy evidence.

! Before isolating hosts, capture volatile memory and running process lists if time allows. Premature shutdown destroys forensic evidence and may not stop encryption on other hosts already seeded.
Step 1 — Capture Volatile Data (Before Isolation)
Linux — Capture memory and process state
# Record running processes with full command lines
ps auxf > /tmp/processes_$(hostname)_$(date +%Y%m%d_%H%M%S).txt

# List all open network connections
ss -tulnp > /tmp/netconn_$(hostname)_$(date +%Y%m%d_%H%M%S).txt

# Record active users
w > /tmp/users_$(hostname)_$(date +%Y%m%d_%H%M%S).txt

# Hash suspicious binaries before anything changes
sha256sum /path/to/suspicious/binary > /tmp/hashes.txt

# Copy volatile artifacts to IR jump box before isolation
scp /tmp/*_$(hostname)_*.txt ir-analyst@IR-JUMPBOX:/evidence/$(hostname)/
Windows (PowerShell) — Capture volatile data
# Get all running processes with paths
Get-Process | Select-Object Name, Id, Path, StartTime | Export-Csv C:\IR\processes.csv

# Active network connections
Get-NetTCPConnection | Where-Object State -eq 'Established' | Export-Csv C:\IR\netconn.csv

# Scheduled tasks (common ransomware persistence)
Get-ScheduledTask | Where-Object State -ne 'Disabled' | Export-Csv C:\IR\tasks.csv

# Autorun entries
Get-ItemProperty HKLM:\Software\Microsoft\Windows\CurrentVersion\Run
Step 2 — Isolate Infected Hosts
Linux — Network isolation via iptables
# Allow only SSH from IR jump box, block everything else
iptables -I INPUT 1 -s IR_JUMPBOX_IP -j ACCEPT
iptables -I OUTPUT 1 -d IR_JUMPBOX_IP -j ACCEPT
iptables -A INPUT -j DROP
iptables -A OUTPUT -j DROP

# Confirm rules applied
iptables -L -n -v

# Save rules to survive reboot if needed
iptables-save > /etc/iptables/rules.v4
Windows (PowerShell) — Block all traffic except IR team
# Block all inbound traffic
New-NetFirewallRule -DisplayName "IR-Block-Inbound" -Direction Inbound -Action Block

# Block all outbound traffic
New-NetFirewallRule -DisplayName "IR-Block-Outbound" -Direction Outbound -Action Block

# Allow IR team access only
New-NetFirewallRule -DisplayName "IR-Allow-SSH" -Direction Inbound -Protocol TCP -LocalPort 22 -RemoteAddress IR_JUMPBOX_IP -Action Allow
Step 3 — Block Lateral Movement at the Network Layer
Firewall / network-level containment
# Block SMB (445) across VLANs — primary ransomware spread vector
iptables -A FORWARD -p tcp --dport 445 -j DROP
iptables -A FORWARD -p tcp --dport 139 -j DROP

# Block RDP lateral movement (3389)
iptables -A FORWARD -p tcp --dport 3389 -j DROP

# Block WMI and RPC (lateral movement via admin shares)
iptables -A FORWARD -p tcp --dport 135 -j DROP

# If using pfSense or similar — block infected subnet from reaching backup VLAN
# Rule: Source: INFECTED_VLAN / Dest: BACKUP_VLAN / Action: Reject
Step 4 — Kill Malicious Processes
Linux — Kill ransomware process
# Find suspicious processes consuming high CPU (encryption is CPU-intensive)
ps aux --sort=-%cpu | head -20

# Identify the PID of the suspicious process
pgrep -a suspicious_process_name

# Kill the process (do NOT use -9 unless necessary — may corrupt forensic state)
kill -15 PID

# If process respawns, check for persistence mechanisms
crontab -l
systemctl list-units --type=service --state=running
ls -la /etc/cron.d/ /etc/systemd/system/
Windows (PowerShell) — Kill ransomware process
# Find high-CPU processes
Get-Process | Sort-Object CPU -Descending | Select-Object -First 10

# Kill suspicious process by name
Stop-Process -Name "malicious_process" -Force

# Kill by PID
Stop-Process -Id PID -Force

# Disable malicious scheduled task
Disable-ScheduledTask -TaskName "SuspiciousTaskName"

# Remove malicious service
Stop-Service -Name "MaliciousService"
sc.exe delete "MaliciousService"
Containment Checklist
  • Volatile data captured from all confirmed infected hosts
  • Infected hosts isolated from network (firewall rules applied or physical cable pulled)
  • SMB (445), RDP (3389), and WMI (135) blocked at inter-VLAN firewall
  • Domain Controllers assessed — if not encrypted, isolate them proactively
  • Backup systems confirmed unreachable from infected VLAN
  • VPN access suspended for all users pending investigation
  • Compromised accounts disabled in Active Directory
  • Malicious processes terminated on all confirmed hosts
  • All actions timestamped in incident timeline log
Phase 4 Eradication NIST SP 800-61 § 3.3

Eradication means removing every trace of the attacker from the environment — not just the ransomware binary. If attacker access paths (persistence, backdoors, compromised credentials) are not fully eliminated, the adversary will re-enter and re-encrypt within days.

Identify and Remove Persistence Mechanisms
Linux — Check common persistence locations
# Check all crontabs (root and users)
crontab -l
cat /etc/crontab
ls -la /etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/

# Check for malicious systemd services
systemctl list-units --type=service
ls -la /etc/systemd/system/ | grep -v "^total"

# Check bash profile modifications (common for backdoor persistence)
cat ~/.bashrc ~/.bash_profile /etc/profile /etc/profile.d/*

# Find SUID/SGID binaries that shouldn't exist
find / -perm /4000 -o -perm /2000 2>/dev/null | grep -v /usr

# Check for new users added during compromise window
awk -F: '$3 >= 1000' /etc/passwd
lastlog | grep -v "Never logged in"
Windows (PowerShell) — Remove persistence
# Check Run keys for malicious autoruns
Get-ItemProperty HKLM:\Software\Microsoft\Windows\CurrentVersion\Run
Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run

# Remove a malicious registry autorun entry
Remove-ItemProperty -Path "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run" -Name "MaliciousEntry"

# Delete malicious scheduled tasks
Get-ScheduledTask | Where-Object TaskName -like "*suspicious*" | Unregister-ScheduledTask -Confirm:$false

# Remove malicious WMI subscriptions (advanced persistence)
Get-WMIObject -Namespace root/subscription -Class __EventFilter | Remove-WmiObject
Get-WMIObject -Namespace root/subscription -Class __EventConsumer | Remove-WmiObject
Get-WMIObject -Namespace root/subscription -Class __FilterToConsumerBinding | Remove-WmiObject
Credential Reset — All Privileged Accounts
  • Reset KRBTGT account password twice (48 hours apart for Kerberos ticket invalidation)
  • Reset all Domain Admin and Enterprise Admin passwords
  • Reset all service account passwords
  • Revoke all active VPN sessions and require re-authentication
  • Invalidate all OAuth tokens and API keys used on affected systems
  • Reset local Administrator passwords on all endpoints (use LAPS or equivalent)
  • Disable or delete accounts created by the attacker during compromise window
Malware Removal and System Validation
Scan for known ransomware IOCs
# Search for known ransomware binary names and extensions
find / -name "*.locked" -o -name "*.enc" -o -name "README_DECRYPT*" 2>/dev/null

# Search for recently modified executables (last 7 days)
find /usr /opt /tmp /var -mtime -7 -type f -executable 2>/dev/null

# Hash all suspicious files and cross-reference against VirusTotal
sha256sum /path/to/suspicious_file

# Run ClamAV scan if available
clamscan -r --infected --remove /home /opt /tmp

# Check for unusual listening ports post-containment
ss -tulnp | grep -v "LISTEN.*127.0.0"
! Do not rebuild systems from the same base image if the attack vector was a vulnerability in that image. Patch first, then reimage. Validate the clean image before deploying.
Eradication Checklist
  • All malware binaries identified, hashed for evidence, and removed
  • All persistence mechanisms removed (registry, cron, services, WMI subscriptions)
  • All compromised accounts disabled or reset
  • KRBTGT reset twice if AD was accessed by attacker
  • Clean system images validated against known-good baseline
  • Patch or remove the initial access vulnerability (CVE reference if known)
  • IOC list compiled: file hashes, IPs, domains, process names
  • IOCs submitted to threat intelligence platform and EDR blocklist
Phase 5 Recovery NIST SP 800-61 § 3.4

Recovery restores affected systems to full operational status. The order of restoration must be driven by business criticality. Do not reconnect systems until they are validated clean — a single reinfected host can re-encrypt the environment.

! Confirm with legal and CISO before restoring from backup. Depending on jurisdiction, if data was exfiltrated (double-extortion), regulatory notification timelines may have started. Recovery does not reset the notification clock.
Recovery Priority Order
Priority 1 — First 4 hours
Core infrastructure: Domain Controllers, DNS, DHCP, authentication services. Without these, nothing else can be restored safely.
Priority 2 — Hours 4 to 12
Business-critical systems: ERP, financial systems, production databases. Validate backup integrity before restore.
Priority 3 — Hours 12 to 48
Operational systems: email, collaboration tools, file shares. Validate clean state before connecting to network.
Priority 4 — Day 2 to 7
Non-critical endpoints and workstations. Reimage from validated clean baseline — do not restore encrypted endpoints from backup unless forensically necessary.
Backup Validation and Restore
Validate backup integrity before restore
# Verify backup hash matches pre-incident baseline
sha256sum /backup/path/system_backup.img
# Compare output against stored baseline hash in your backup registry

# Test restore in isolated environment first (not production network)
# Mount backup as read-only to inspect for compromise artifacts
mount -o ro /dev/backup_device /mnt/validate

# Confirm last clean backup date — check backup logs
cat /var/log/backup/backup.log | grep -i "success" | tail -20

# Restore specific directory from backup (rsync example)
rsync -avz --checksum /backup/clean_snapshot/ /restored/target/
Post-Restore Validation
  • Restored system booted and verified clean by EDR scan before network reconnection
  • Wazuh agent reinstalled and reporting to manager (verify in dashboard)
  • FIM baseline re-established on restored hosts
  • Authentication tested with new credentials (old credentials must not work)
  • Application functionality verified by system owner before declaring operational
  • Enhanced monitoring enabled on restored systems for minimum 30 days
  • Business unit sign-off documented before declaring recovery complete
Decryption Options (If No Clean Backup)

Evaluate In This Order

  • Check No More Ransom (nomoreransom.org) — free decryptors for many known strains
  • Engage IR retainer firm — some have decryption keys from previous cases
  • Check if encryption was incomplete — partially encrypted files may be partially recoverable
  • Evaluate ransom payment only as last resort after legal and CISO sign-off — payment does not guarantee decryption and may violate OFAC regulations if group is sanctioned
+ Recovery is complete only when all critical systems are operational, enhanced monitoring is active, and the business unit has provided written sign-off. Document the completion timestamp for SLA and insurance reporting.
Phase 6 Post-Incident Activity NIST SP 800-61 § 3.4

The post-incident phase turns a painful event into organizational improvement. Every ransomware incident contains lessons that can prevent the next one. Organizations that skip this phase are statistically more likely to be re-attacked within 12 months.

Reporting Requirements

Internal Reports

  • Executive incident summary (non-technical, 1 page)
  • Technical incident report (full timeline, IOCs, root cause)
  • Business impact assessment (downtime, cost estimate)
  • Control failure analysis (what controls failed and why)

External Notifications

  • Regulatory: HIPAA (60 days), SEC 8-K (4 business days if material), State AG
  • Cyber insurer: notify within policy SLA window
  • Law enforcement: FBI IC3, CISA reporting if critical infrastructure
  • Affected customers/partners if PII or PHI was exfiltrated
30-Day Post-Incident Hardening Sprint
  • Root cause remediated and validated closed
  • All IOCs added to EDR blocklist and SIEM detection rules
  • Wazuh custom rules updated to detect the specific TTP chain observed
  • MFA enforced on any remaining systems that lacked it
  • Backup schedule reviewed — test restore cadence increased if deficient
  • Network segmentation gaps identified and remediation scheduled
  • Phishing simulation run if initial access was email-based
  • Tabletop exercise scheduled using this incident as the scenario
  • Playbook updated with lessons learned from this incident
MITRE ATT&CK — Ransomware Technique Reference

The following MITRE ATT&CK techniques represent the typical kill chain observed in modern ransomware operations. Mapping attacker behavior to this framework enables faster detection, accurate threat intelligence sharing, and structured defensive coverage analysis.

Technique ID Tactic Name Ransomware Usage Wazuh Detection
T1566 Initial Access Phishing Malicious email attachment or link — most common ransomware entry point Email gateway logs, Rule 40111
T1190 Initial Access Exploit Public-Facing Application VPN vulnerabilities (Fortinet, Pulse), Exchange ProxyShell, web app exploits Web logs, IDS alerts, Rule 100200
T1078 Initial Access / Persistence Valid Accounts Stolen credentials from prior breach or dark web purchase used for access Rule 40111, Wazuh authentication events
T1059 Execution Command and Scripting Interpreter PowerShell, cmd.exe, WScript used to execute payload stages Sysmon Rule 92200, PowerShell logging
T1055 Defense Evasion / Privilege Escalation Process Injection Injecting into legitimate processes (svchost, explorer) to evade AV detection Sysmon Rule 92200
T1562 Defense Evasion Impair Defenses Disabling Windows Defender, removing AV, clearing event logs before encryption Rule 61604, Rule 92656
T1070 Defense Evasion Indicator Removal Clearing Windows event logs, deleting files, modifying timestamps Rule 92656
T1112 Defense Evasion Modify Registry Disabling recovery options, adding autorun persistence, modifying security settings Sysmon registry events
T1018 Discovery Remote System Discovery Scanning the network for additional targets before mass encryption Network flow analysis, Wazuh IDS
T1083 Discovery File and Directory Discovery Enumerating file shares and network drives to maximize encryption impact Sysmon, FIM Rule 550
T1021 Lateral Movement Remote Services SMB, RDP, WMI, PsExec used to spread to additional hosts Rule 40111, network firewall logs
T1041 Exfiltration Exfiltration Over C2 Channel Double-extortion groups exfiltrate data before encrypting (Cl0p, LockBit, BlackCat) Rule 100200, DLP alerts, DNS logs
T1489 Impact Service Stop Stopping database services, backup agents, and AV before encryption begins Wazuh service monitoring
T1490 Impact Inhibit System Recovery Deleting VSS shadow copies, disabling Windows Recovery Environment Rule 31168 — highest signal rule for ransomware
T1486 Impact Data Encrypted for Impact Core ransomware behavior — encrypting files with asymmetric or symmetric encryption Rules 87103, 87105 — mass FIM triggers
T1485 Impact Data Destruction Some groups destroy backups or wipe systems if ransom is refused Rule 554 (mass deletion), FIM monitoring
